feat(web): 分类色板（方案甲）—— 色值迁移彻底收口，全仓 0 处游离色值

用户裁决采用甲方案（受限色板）。

## 先纠正一个前提：「不与状态色相撞」做不到

D 锁定了 7 个有彩色相的状态色（h8 是灰），散布在整个色轮上：

   33.6 h6 返工待派   131.8 h7 已结单   267.2 h4 已挂起   288.6 h3 维修中
   63.8 h1 待派单     196.4 h2 待承接                     310.5 h5 待验收

最大空档只有 83.1 度。要再塞 8 个新色相、且每个离所有状态色 dE > 15 —— 算术上做不到。
所以「受限」能限住的只有明度与彩度，「避开状态色」只能做到尽量远。
这一条必须先说清楚，否则会去优化一个不存在的目标。

## 改前那 8 个色：4 个就是状态色本身

  #1677FF = h3 维修中  dE=0.0     #722ED1 = h5 待验收  dE=0.0
  #52C41A = h7 已结单  dE=0.0     #13C2C2 = h2 待承接  dE=0.0
  #FAAD14 ~ h1 待派单  dE=19.6  <- 而且它是被废弃的旧「已挂起」色

明度极差 38.1（紫 L*=38.1 vs 琥珀 L*=76.2）——同一张饼图里紫色那块比琥珀重一倍，
而这两个分类没有任何轻重之分。彩度极差 94.5（纯灰 C*=0 混在 C*=94.5 旁边）。

可读性本来没问题（相邻 dE 最小 48.9）。所以这不是「看不清」，
是「借来的颜色」+「随机的重量」两个问题。

## 色板是推出来的，不是手挑的

三个参数：明度 L*、彩度 C*、色相起始角 offset。前两个是设计取舍，第三个可以算：

  best offset = 39 度  ->  min dE to any status hue = 19.6
  （随手取 20 度只有 13.3）

39 度是 0~44 全扫一遍取的最优 —— 这一步值得做，它把「尽量避开状态色」
从一句口号变成了一个可以被优化的量。

## 等 Lab 彩度在数值上齐，但看起来发闷

第一版一律 C*=34，L* 极差 0.2 / C* 极差 0.5，数字上完美 —— 但看图上发现它发闷：
暖色在等 Lab 彩度下看起来比冷色更灰。根因是 Lab 的 C* 不是感知彩度，
黄/橙要更高的 C* 才和蓝/青一样「有色」。

改成「各色相取 sRGB 能给的最大彩度、再封顶 55」，四个变体并排看完后取 C：

  A  L*=60 等彩度 34（数值最齐，发闷）      L*sp 0.2  C*sp  0.5  toStatus 19.2
  B  L*=60 各色相取满（黄特别重）           L*sp 0.6  C*sp 47.6  toStatus 13.4
  C  L*=60 取满但封顶 55   <- 采用          L*sp 0.3  C*sp 21.0  toStatus 19.6
  D  L*=66 取满封顶 55                      L*sp 0.2  C*sp 18.2  toStatus 17.1

A 在四条判据上都是最好的，而它是要被淘汰的那个 —— 是「看一眼」把它淘汰掉的。
方法论：数值齐不等于看起来齐。

## 落地

色值进 tokens.css 的 --cat-1..8（§3.2b），组件只按序取。
判据锁在 category-palette.spec.ts（7 条）：等明度 / 彩度可比 / 相邻 dE /
避开状态色 / 反向自证不再借用那 4 个状态色。

还有一条性质写进注释但没修：色板按下标取，同一个「水暖管道」两次刷新可能不同色。
这是改前就有的，要稳定映射得由后端给分类发固定序号。

## 棘轮闭合：UNMIGRATED 名单空了

DashboardView.vue 是全仓最后一个有色值字面量的文件。它剩下的 7 个 # 不是普通字面量，
而是 cssToken('--name', '#value') 的 fallback 参数：图表必须在渲染时读令牌，
读不到时要有兜底；那是令牌的第二处声明，不是绕开令牌层。

但光豁免就是个后门（写个错的 fallback 就能藏任意色值）。所以做成豁免 + 镜像断言：
  · codeOf 把 cssToken('--x','#...') 中性化
  · 新增用例「每个 fallback 必须等于 tokens.css 里那个令牌的真值」
  · 新增用例「反向自证：同样的色值只要不在 cssToken 里，照抓不误」
一句话：豁免掉的那部分不是我信任它，是我另外派人盯着它。

## 同一套口径漂成了三份，三个数字各自都能自圆其说

「怎么算一个色值字面量」在仓里有三份实现：棘轮（权威）/ scan-hex（盘点）/ 主探针。
给棘轮加上 fallback 中性化之后，另两份都没跟着改：

  棘轮报 DashboardView  0 处
  另两份报 DashboardView 14 处

你去看哪一个都觉得它对。这是最难发现的一类不一致。
按本仓既有取舍（tokens.css<->status.ts 那套）：冗余保留，
但把「三处必须一致」变成机器判据 —— 新增用例抽三份的扫描链逐条比对。

## 这条同步断言自己踩了两个坑

1. 第一版用「指纹子串」，连块注释那条都对不上 —— 转义写法与文件里的不是同一个串。
   于是「通过」的含义悄悄变成了「我碰巧挑中了几个能匹配上的子串」。
   改成抽扫描链后才有意义。
2. 负向对照因为改错地方而「通过」：我把 const CSS_TOKEN_FALLBACK 改名，测试照样绿，
   因为函数体没变。改成摘掉那一条 .replace(...) 才红。
   顺带记一条操作教训：那次负向对照的 finally 里 Move-Item 用了相对路径而 try 里 cd 过，
   还原失败、文件被留在改坏的状态；重做两次并改绝对路径才对。

## 顺手修掉一个「把成功当故障」的守卫

主探针的 listFromSpec 原本写着「解析出 0 项 = 解析器坏了，不是名单为空」。
当时那是对的（UNMIGRATED 不可能为空），而本批它真的空了 ——
于是这条守卫把成功当成故障，整条探针在开头就抛掉（PASS=0/FAIL=0，看着像探针坏了）。

改法：守卫换到 MIGRATED 上证（它永远非空）。原来那条性质一点没丢，只是换了个人去证。
